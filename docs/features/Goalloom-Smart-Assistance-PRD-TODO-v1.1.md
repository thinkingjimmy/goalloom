## 0. 交付范围与阅读方式

### 0.1 一句话目标

**普通任务仍然快速记录、直接完成；详情用可核对的执行事实提醒用户重新确认安排，用户需要帮助时，再结合相同事实提出一个可编辑、可采用、可撤销的推进调整。**

本次主交付为：

- 统一 Jev 智能整理与 DeepSeek 起草、复盘、卡点帮助的相关上下文、能力边界和结果处理方式，但不强制双模型串行。
- 新增任务内的「卡住了…」入口，以及有界的说明／追问／建议流程。
- 将用户采用的建议落为任务的“推进说明”，必要时与一次明确的排期调整原子提交。
- 补齐数据持久化、精准撤销、历史／备份／恢复、请求取消、权限同意和五语言验收。
- 将现有详情右栏的顺延统计优化纳入**核心交付**：准确口径、适度且可解释的压力、可追溯月历、“卡住了”入口，以及 UI／AI 共用的执行事实摘要。

**范围裁决：本次先不实现完整习惯运行引擎。**前面的习惯方向没有被删除，完整接入要求保留在附录 H，并有独立的 Markdown TODO。此裁决是对最近讨论“以智能服务升级为主线、不让习惯系统阻塞卡点帮助”的落实建议，不是声称用户已批准延期。主交付不得展示“创建习惯／每天自动生成／打卡统计”等尚未实现的按钮或承诺。若本次版本要包含习惯，附录 H 的任务与验收必须全部纳入发布门槛，不能只修改提示词。

## 2. 产品体验与不变项

### 2.1 四个场景，一套基础能力

| 场景 | 用户入口 | 模型策略 | 写入规则 |
| --- | --- | --- | --- |
| 记录任务 | 现有全局输入／列内新建 | 全局沿用 Jev；列内不新增模型调用 | 现有预览／确认与快速新建不变 |
| 起草下一步 | 现有断点、拆解、空列入口 | 直接调用既有 DeepSeek 路径 | 已有一键单条起草语义保留 |
| 推进困难 | 新增「卡住了…」 | 直接调用 DeepSeek，不先让 Jev 判断按钮意图 | 只生成建议，用户确认后采用 |
| 周期复盘 | 现有复盘入口 | 程序给事实，DeepSeek 组织文案 | 复盘不直接修改当前任务 |

统一的是能力路由、字段含义、上下文构造与失败处理，不是把所有入口改造成同一张聊天面板。

### 2.2 主路径不变

普通新增仍然直接输入；不先问“任务还是习惯”，不要求选择心理学方法。没有推进说明的任务保持原行高和正文密度。保留 1.5.0 已有的详情右栏，在其中优化本地统计；不得另增常驻 AI 聊天侧栏、“受阻任务”列、连续打卡计数、默认强制问卷或自动弹窗。

「卡住了…」是一次操作，不是给任务贴永久标签。保存后展示“下次先写两个例子”，而不是“你已经拖延三天”。

### 2.3 入口与可用范围

- 看板 `TaskMenu` 的推进相关分组增加入口；详情入口放在现有 `detail-rail` 的执行摘要下方、活动月历上方。最新 ItemDetail 已没有更多菜单，不得为此恢复旧菜单；不放到每个看板行的常驻主按钮上。[C29]
- 可用于当前、未来及往期中仍为 `todo`、未删除、未归档的条目，包括 Later；Later 只能保存推进说明或明确移动，不能新建关联。
- 完成／取消／归档／回收站条目可查看既有推进说明，不接受新的 AI 采用。用户需要先按现有操作重新打开或解除归档。
- 复盘只读记录不增加此入口；用户回到看板后再操作。
- 无 AI 时入口可提供手写推进说明与现有排期入口，连接说明只在用户主动要求 AI 时出现，不循环推销。

### 2.4 主流程

1. 用户选择「卡住了…」。来自详情时先结束 IME 组合并 flush；保存失败留在原界面，不把未保存的文本当作已保存上下文发送。
2. 本地读取当前任务及有界相关上下文。仅打开窗口不发网络请求、不写工作区。
3. 展示任务标题、已有推进说明及输入：“现在最难推进的是什么？”用户可写一句，或点击可选的快捷答案。
4. 用户点击“帮我想个办法”；有新的数据发送范围时先明确同意。若不愿描述，另有“先根据任务给个思路”，这同样是显式生成操作。
5. DeepSeek 返回一个建议，或一个必要的澄清问题。最多自动提出一个澄清问题；每次后续生成均由用户触发，不自循环。
6. 用户编辑建议并确认实际变化。无日期调整时主按钮为“保存推进说明”；有明确移动时为“采用并调整安排”。
7. 权威事务成功、回执已确认后回到原任务。给出“已更新推进说明”等事实反馈及撤销入口，不说“问题已解决”。

### 2.5 一个具体例子

任务：完成 Token 教程初稿。已有说明：概念部分已写完。用户补充：“例子总觉得不好，来回改，推进不下去。”

建议应从已有事实继续，例如：

> 这次先把一个现有例子整理成“原句、拆分结果、解释”三部分；拿不准之处先标注，暂不处理插图。

用户采用后保存为当前推进说明。不得重新生成“选题—列大纲—写初稿”通用清单，不得把“写一个例子”自动替换为整个任务的完成标准，不得自动把任务标为完成。

### 2.6 多轮与关闭

采用有界会话，不做长期聊天历史。会话内至多三次用户主动生成（首次、澄清后、一次调整）；达到上限后仍可手工编辑、采用或开启新的求助。该上限是成本／交互初始参数，不是模型能力限制。

main 只在会话内保留已通过校验的逐轮用户输入和模型问题／建议；后续请求必须携带这些记录，使“前者”“缩小这一步”保留指向，用户补充的进展不能因进入调整轮而丢失。renderer 不提供或伪造模型会话。会话正文计入原 512 KiB 内存上限，合并提示计入 16,000 code units / 64 KiB 上限；取消、关闭、新预检和失效均清理，不入库或导出。

关闭普通草稿时取消该会话请求，当前窗口会话可保留最多八个任务草稿，LRU 总量不超过 512 KiB；重启不保证恢复未采用会话，界面说明只出现在确有未保存内容时。工作区替换、遗忘服务时清空。已采用推进说明持久化。

写入回执未知时不得关闭并丢弃待核对命令；沿用现有 pending/receipt 恢复规则。请求生成与业务写入是两种不同状态，不能用一个“取消”按钮假装撤销已提交的事务。

## 3. 可采用的动作与边界

### 3.1 本版白名单

| 动作 | 数据结果 | 不能做什么 |
| --- | --- | --- |
| 明确下一步 | 保存 `next_step` 推进说明 | 不生成一组新任务，不自动改变完成标准 |
| 缩小本次尝试范围 | 保存 `working_scope`：本次做到哪、暂不做什么 | 不偷偷重命名或缩减整个目标 |
| 留下继续位置 | 保存 `resume_point`：做到哪、接下来做什么 | 不把模型猜测当作用户已完成的工作 |
| 记录等待条件 | 保存 `waiting_note` 的文字 | 不增加受阻状态、不自动催人、不声称到期提醒 |
| 调整当前任务的安排 | 用户确认具体目标周期后复用 move 语义 | 不自动改 dueDate、完成状态、颜色或关系；Later 例外必须明确预览 |

一份建议最多包含一份推进说明和一次移动。若同时采用，必须原子提交和整体撤销。不得连续调用 `edit` 与 `move` 后显示一条“全部成功”。

### 3.2 现有能力的明确交接

用户确实需要拆解时，提供“回到拆解”入口，走既有 Seeded／decompose 路径，不在本版 `applyAssistance` 中新增 createPlan、改关系或删除动作。今天列无更短周期，不能创建同周期上下级。

用户想取消任务时，可在现有任务菜单或详情右栏自行操作；模型不输出可直接取消或删除的指令。用户只是没有时间时，允许直接打开排期，完全不调用模型。

### 3.3 等待不等于暂停

本版 `waiting_note` 是说明，不改变原来的自动顺延规则，也不提供复查调度。确认界面明确写“仅记录等待条件，安排不变”。“周五再看看”可以是用户写下的文字，不渲染为已经生效的提醒控件。

移入 Later 时列出会解除的上级关联及数量，要求明确确认。不得默认把“在等图片”转换成移入 Later。真实截止日期始终保留；移动到截止日期之后显示冲突说明。

### 3.4 习惯建议与情境句式

AI 可以按需提出“用一个稳定情境支持重复行动”这样的文字建议，但本版只保存说明，不建立频率规则。主按钮不得称“建立习惯”；界面明确“这是推进建议，尚未设置重复执行”。不应以此伪装完整习惯支持，也不在每个普通任务里强行加入该句式。

附录 H 完成之前，模型允许动作集合不包含 `create_habit`，程序也拒绝该类输出。后续能力是否可用由实际实现决定，不再设计用户可见的插件总开关。

## 4. 模型协作、上下文与质量

### 4.1 路由原则

现有明确入口直接选择能力。普通全局输入沿用 `analyze`；「卡住了」直达生成通道；起草／复盘继续使用原入口。不得固定 Jev → DeepSeek → Jev 审核，不为简单输入增添一轮生成。

Jev 的结构化选择／评分／布尔概率适合有界判断，不提供自由文本方案。[W01] DeepSeek JSON 模式便于解析，但仍需处理空内容、截断和格式异常。[W02] 二者的结果都不是业务权限或事实真值。

本版不更改固定模型、服务路由、SDK 依赖或推理开关。迁移或更换模型必须另有真实场景评测，不能以“更智能”为理由自动开启高成本路径。

### 4.2 权威上下文

新增 main 侧上下文构造器，经 storage worker 做短只读查询；网络请求在 main，绝不持有 SQLite 写事务。renderer 发送任务身份和用户输入，不发送可被当作权威事实的任意整张看板。

| 内容 | 初始上限与选择规则 |
| --- | --- |
| 当前任务 | 标题、状态、实际位置、期限；说明最多 6,000 UTF-16 code units |
| 当前推进说明 | 完整、上限 1,200 code units；明确来源为用户采用／手写 |
| 上级目标 | 最多 3 个，按现有看板顺序；多父关系不虚构唯一主父 |
| 当前活跃下级／同级 | 分别最多 8 项，只给标题、状态、位置与必要摘要 |
| 已采用的历史调整 | 最多最近 2 份，单份有界；不读取原始聊天 |
| 日期 | 工作区 timezone、当前业务日期、相关实际 period 边界 |
| 执行事实 | §6A 的相同权威摘要；最多 6 条相关活动证据，不发送全部历史。每个指标带口径、范围、质量与截至时间 |
| 能力与偏好 | 仅本次允许动作、有效服务／同意范围、语言与相关偏好 |

完整上下文正文总量上限为 16,000 code units，序列化请求上限 64 KiB；超限时按“当前任务与用户本轮输入优先”裁剪。返回 `truncatedSections` 与省略数量，不让模型假定看到全部内容。单条用户输入最多 2,000 code units，输出最多 64 KiB。

不抓取 URL 指向的正文、不访问文件路径、不遍历整个关系图、不读取无关目标、邮件或浏览器。用户说明中的命令／网址均视为不可信数据，不是工具指令。

### 4.3 上下文共享不是把同一大包发给所有模型

新增共有的任务身份、周期事实、推进说明、来源／缺失标记定义；为 Jev、起草、复盘、辅助分别做投影适配。已有 Jev `SmartContext` 和输入法式预览语义不需要被整体重写。

当前推进说明可用于之后的起草，防止重复建议已做步骤；但“用户打算做”不能自动变成“用户已经做完”。执行摘要在用户请求帮助或既有复盘生成时按需加入，不为普通 Jev 输入增加活动扫描或模型调用；记录不足时保留 unknown。不要因为保存说明就停止已有断点判断，或把文本推断成真实下级任务。

### 4.4 复盘保持时间边界

回顾过去使用截止时的状态和当时已经存在的推进说明。当前说明只能用于“下一期建议”，不能写进过去事实。回顾对象与未来安排对象分开传给模型。

若历史只有 baseline、不足以可靠还原某份说明或执行指标，标注 unknown 并省略事实性结论。不得用最新值倒填；后来的撤销也不能改变在旧截止时刻生成的事实投影。历史期限没有可追溯来源时，不拿当前 dueDate 计算“当时已逾期”。已有复盘入口、只读行为、确认／跳过、缓存和完成撒花保持原契约。

### 4.5 输出要求

输出一个主要可行方案，不输出十条任务或长篇鼓励。解释只陈述建议依据与实际变更，不输出私有推理过程，不给人格／心理诊断。

明确区分“用户提供”“程序事实”“模型建议”。模型猜测必须以问题或不确定表达出现。无法解决技术细节时可以建议复现、验证或找人确认，不编造已经读取的代码、网页和外部数据。

对健康、财务等高风险目标只提供任务组织层面的帮助；不从“减重 10kg”等目标直接推断个体化医疗／饮食方案。这个功能不是专业诊断工具。

## 5. 交互呈现与设置

### 5.1 辅助窗口

复用现有 Modal／Popover、Hugeicons、纸感／简约及明暗 token。优先在详情内切换到辅助子视图；不得叠加两个相互争夺焦点的原生模态框。从任务菜单打开时保留原行定位与虚拟列表锚点。

初始只有任务信息、已有推进说明、一处输入和生成按钮。原因选项是可选快捷填充，不是必填诊断问卷。生成时可取消，失败保留输入；不因结果到达抢焦点或覆盖用户正在编辑的建议。

结果展示“建议做法”和“采用后实际变化”。移动发生时给出具体日期／周期，不只写“以后”；一次跨午夜后实际目标变化必须重新预览。

### 5.2 推进说明的展示

详情中只有存在记录时才出现一块紧凑的“推进说明”，可编辑、清除；没有记录不占空间。编辑保存使用专用命令与局部确认，不改变原标题、说明和期限的静默 autosave 习惯。

看板有原说明时保留原 NoteSignal 和清单进度优先级，以同一预览中的次级入口显示推进说明；无原说明时可在既有信号位置显示一行推进摘要。不得增加第二套巨大卡片、挤掉真实期限或把每项元数据都展开成一行。

关闭 AI 后已保存说明仍可查看、手工编辑、删除。它是工作区数据，不依赖模型在线。

### 5.3 设置与授权

产品文案统一为“智能辅助”，但内部保留 `smart` / `insight` capability、各自服务选择与 revision，不迁移为一个含义含混的总开关。既有断点与复盘提示开关继续独立，不因关闭文字生成而消失。

新辅助沿用 insight 的生成服务。只有 Jev 可用时，不悄悄寻找另一个服务；显示手工方案与连接／重测入口。失败不切换 provider，不自动提升模型或费用。

新增 purpose consent：发送当前任务正文、相关目标摘要和本次求助文本之前，按实际服务明确同意。建议提示：

> 这次会向所选 AI 服务发送当前任务说明、有限的相关目标、顺延与安排等执行摘要，以及你输入的困难。不读取链接中的网页内容，也不发送全部活动历史。

读取本地上下文不等于网络同意。服务连接测试使用非私人样例，不能顺便发送用户数据。旧的服务同意不自动获得新正文范围权限。

设备配置建议升级 v3，在每个 provider 下保存有版本的 `assistanceConsent`；旧 v1/v2 的 Key、能力测试、既有开关、绑定代次和失败记录保持，新增 consent 默认为空。不是给习惯新增一个功能开关。

### 5.4 详情右栏：事实 → 推进帮助 → 活动 → 管理操作

本节为核心需求。沿用最新永久 `detail-rail`、正文区域、顶部位置与流标签；不更换主看板形态，不新建统计中心。右栏上方为可独立滚动的信息区，原取消／归档／删除管理区保持独立、可达；长明细不得将管理按钮挤出可操作区域。[C29]、[C37]

推荐顺序：

1. **执行摘要**：一个主事实，最多两条次要事实；未知字段不补零。
2. **推进帮助**：同一行“卡住了？”与次要“调整安排”；低强度时为安静文字入口，高强度仅提升该帮助的可见性。
3. **活动月历与按日明细**：保留现有月历，用来定位真实发生操作的日期。
4. **管理操作**：原取消、归档、删除，不挪到新 AI 流程里。

示意（数字仅说明排版，不是复算用户截图中的私有任务）：

```text
已顺延 1 次
其中：系统自动 1 次
在「本周」列累计待办约 9 天

卡住了？                     调整安排
──────────────────────────
2026 年 10 月                 ‹   ›
……活动月历……

10 月 5 日 · 1 条记录
未完成后顺延：上周 → 本周 · 系统自动

查看全部活动
──────────────────────────
取消    归档    删除
```

上例三条摘要是上限，不要求同时展示。主标题优先级是：真实逾期 → 当前未完成轮次的有效顺延 → 当前安排事实 → 创建日期。历史最多停留的列降为详情／展开信息，不再覆盖当前事实。没有进入当前有效排期的未来任务显示“计划于……”，Later 显示“尚未安排”，不因存在时间长而显示催办警告。

### 5.5 有力度但可解释的压力

目标是提醒用户重新作决定，不是判断意志力或人格。压力来自真实计划变化和当前期限；不创建“拖延分数”，不按次数改变流程颜色，不用“失败／浪费／你又拖延”等归因词。以下阈值是可测试的产品默认建议，**不是心理学常数，也不是已经证明有效的干预**。

| 层级 | 建议初始规则 | 展示与动作 |
| --- | --- | --- |
| 普通事实 | 无有效顺延，或尚未排入当前／往期计划 | 中性色；展示当前安排／创建日期；不主动提示风险 |
| 已发生顺延 | 本轮存在至少一次 §6A.1 定义的未完成后顺延 | “已顺延 N 次”，可展开来源；保留安静的“卡住了？” |
| 需要重新确认安排 | 日尺度：本轮近 14 个本地日期内涉及至少 3 个不同已结束日周期；周尺度：本轮近 8 个周周期内涉及至少 2 个不同已结束周周期。还须发生在至少两个不同操作日期；月及更长尺度首版不设次数升级阈值 | 一处克制强调色；“这件事还按原计划推进吗？”；突出卡点帮助，不弹窗 |
| 真实截止风险 | 活跃未完成任务的明确 dueDate 早于当前工作区日期 | “已超过截止日期 N 天”；保留调整出口，不自动改期限 |

“需要重新确认”仅使用有效、可完整解释的来源周期计数；单次跨过七天仍是一次操作，不能满足三个来源周期条件。自动和手动都可以说明计划被延后，但始终写清来源，不将 system 次数说成用户再次承诺的次数。混合日／周／月次数不相加套同一阈值；未来提前改期不进入压力计数。

窗口按**操作发生的工作区本地日期**筛选，并受同一 `asOf` 截止时刻与当前活跃轮次约束。日窗口包含截至业务日期的最近 14 个本地日期（含当天）；周窗口包含当前工作区周及之前 7 周，按 `weekStart` 划界。窗口内仅纳入 §6A.1 的有效顺延，分别对来源 periodId 和操作本地日期去重；周窗口不是固定秒数。实际窗口边界、去重数、阈值判断和最终压力等级由 §6A.5 的权威摘要返回，界面不从最多六条活动证据反推。

已有用户采用的 `waiting_note` 或刚确认的新推进方案时，不重复强化同一条次数提示；以该说明的更新时间/记录序列作为去重边界，直到之后出现新的有效顺延来源周期再重新评估。等待说明不改变任何排期或自动顺延规则，也不从“周五看看”文字创建复查调度。**真实截止风险不受该提示去重影响。**

当前与历史计算都按事件顺序重放说明的设置、清除和撤销。清除后不再沿用旧确认边界；撤销清除后恢复原说明及其确认边界。历史仅使用 cutoff 之前的记录，不能由今天的 head 或后来撤销倒填。

完成、取消、归档或删除后，停止未完成压力表达，保留可查看的历史事实；重开开始新的活跃轮次，不把前一轮的历史次数再次当作当前失败。没有完整证据时展示“历史不完整”而不是猜测等级。此处只改右栏的语气和层次，不锁定完成按钮，不要求填写延期理由。

### 5.6 月历与活动可追溯性

取消 `activityInsightMinimum = 3` 对版式的控制。所有任务使用同一种右栏骨架：已有事实即展示；新任务只有创建信息也正常。无活动、加载中、加载失败、历史不完整分别显示，不把失败当作零条记录。

日历按工作区 timezone 和 weekStart 呈现，按**操作实际发生日**标记，不把一周后一次性同步伪画为过去每天都操作过。保留每一天的有序事件集合；同日顺延、跨列移动、完成、重开、采用／编辑推进说明可同时存在，不能用一个 `Record<date, singleMark>` 覆盖。圆点只用于定位，文字明细解释类型、来源、原／目标实际周期；图例仅展示当前有意义的类别，不增加大块多色仪表盘。

点击／键盘激活日期后，在月历下面展示当天有界明细；同一天过多事件通过“继续加载”分页。提供“查看全部活动”进入同一右栏的分页列表，并可返回月历，保留所选月份。返回／关闭不改变任何业务数据。使用确切日期和周期范围，不把历史“上周”误写成相对于今天的上周。

日／月查询使用精确的本地 `[start, end)` 区间，次日／次月零点只归属后一个区间；亚毫秒事件不得因 SQLite 日期舍入跨界。分页过滤在 LIMIT 之前完成，DST 的 23／25 小时日期沿用实际日历边界。

被撤销的操作在明细里保留并标注“已撤销”，默认不计入有效次数；实际撤销动作也可查看。明细条数称“活动记录”，不能与摘要中的“有效顺延次数”混为一个指标。同操作内多个 effect 的中间事件按事件顺序保留，但摘要不重复计数。

日期使用可聚焦控件、可读名称和非颜色提示；按日明细不只依赖 title/hover。支持五语言、四外观、weekStart、跨年、长文案、缩放、原生键盘焦点和无鼠标访问。窄窗口不把现有右栏重新改成隐藏式 AI 抽屉；扩展现有 720/1280 宽度验收，正文和动作均可达。

### 5.7 统计与“卡住了”的衔接

点击“卡住了？”进入 §2.4 的同一会话，携带当前 `factsSnapshot`，不另做一套诊断问卷。若正文存在未保存编辑，仍先 flush；失败停留原详情。仅看统计、换月、看明细或展开辅助输入，均为本地操作，**不得调用 AI**。

例：某视频发布任务发生过一次顺延，说明为空。生成应先询问“现在做到拍摄、剪辑还是待发布哪一步？”，不能仅凭创建十三天就写“你拖延了十三天”。得到“粗剪完成，开头不满意”后再针对该障碍提出一个可采用的方案。采用后更新推进说明和相关活动，不能显示“卡点已解决”或把采用事件当完成事件。

“调整安排”直接复用本地排期，无需模型；Later 仍展示解除上级的影响。只有 Jev 可用或生成服务关闭时，统计仍完整可用，“卡住了”保留手写推进说明入口。新增 AI 发送范围包含执行摘要，按 §5.3 同意后才发送。

## 6. 新增契约与生命周期

以下类型是拟新增的工程契约示意，不表示基线已有这些接口。实现必须补齐严格 Zod schema、preload 类型、main 校验及测试，不直接复制为已完成代码。

### 6.1 推进说明

```ts
type GuidanceValue = {
  formatVersion: 1
  kind: 'next_step' | 'working_scope' | 'resume_point' | 'waiting_note'
  nextAction: string             // 必填，最多 600 code units
  contextNote: string | null     // 用户认可的已知进展／条件，最多 300
  scopeNote: string | null       // 本次暂不处理的范围，最多 300
  authorship: 'user' | 'ai_assisted'
}

type GuidanceRecord = {
  itemId: string
  revision: number              // 单调增加；0 表示尚未有过记录
  value: GuidanceValue | null   // null 是清除后的 tombstone，不回退 revision
  updatedAt: string
  operationId: string
}
```

总正文上限 1,200 code units。只保存用户确认过的内容，模型解释、原始困难描述、完整对话、未采用建议均不进入该记录。用户自己的求助输入需要保存时必须显式选入 `contextNote`，不能默认归档敏感内容。

不增加 `blocked`、`started` 等 Item.status。`waiting_note` 只是内容种类，不是影响顺延、完成或提醒的状态。

### 6.2 生成请求与响应

新增 `prepareAssistance`（本地上下文预检）、`assist`（显式生成）和 `cancelAssistance`（会话级取消）。不把新请求塞进原来的 `draft` 标题数组格式。

请求携带 `requestId / sessionId / itemId / generation / inputRevision / manualRevision / featureRevision / contextId / locale / turn`。main 创建短期 `contextId`，绑定当前窗口、任务、代次、相关记录版本与能力；有效期初始为 10 分钟。过期重新读取本地上下文，不自动再调用模型。

```ts
type AssistanceOutput =
  | { kind: 'clarify'; question: string }
  | {
      kind: 'proposal'
      explanation: string
      guidance: Omit<GuidanceValue, 'authorship'> | null
      moveSuggestion: {
        horizon: 'later' | 'year' | 'half' | 'cycle' | 'month' | 'week' | 'day'
        localDate: string | null
      } | null
    }
```

proposal 至少包含一份 guidance 或一个 moveSuggestion；解释最多 400 code units，澄清问题最多 200。模型不能提供 itemId、operationId、任意命令、SQL、文件路径、callback、工具调用或 provider 配置。未知字段严格拒绝。

moveSuggestion 只是草稿；程序依工作区日历归一化为实际目标周期，用户在预览中确认。`later` 不带日期；其他移动必须在写入前解析成明确日期／周期。自然语言“下周”不能在确认后再次由模型解释。

响应完整回显请求身份与修订，并带 `contextId`、截断标记、实际服务标识、结果状态。`ready / failed / cancelled / stale` 区分；不把取消显示为服务故障。

### 6.3 取消和失效

生成前后都复核：当前 generation、insight revision、provider、正文与执行摘要发送 consent、会话是否有效、任务身份和用户手工修订。关闭窗口、切换任务、改服务、关闭 insight、遗忘 Key、重置／恢复工作区均使相关在途请求失效。

基线 insight 路径用 `connections` 集合，原 `cancel` 主要处理分析会话；`feature()` 仅 smart 分支直接 abortAll。[C04] 实现时需要目的明确的请求登记／取消，不假设现有 cancel 已覆盖新面板。网络真的取消与 UI 忽略迟到回复两者都要测试。

取消一个辅助会话不得误杀其他正常复盘或连接测试；切换／遗忘同一 provider 时则取消依赖该配置的请求。状态切换要贯穿 preflight、网络、解析与返回，不只在 fetch 后做一次检查。

### 6.4 缓存与离线

新辅助的上下文和未采用内容只做会话内有界缓存，不落盘。缓存键至少含 generation、itemId、依赖快照、provider/model、featureRevision、consentVersion、locale、提示词版本与用户文本／手工修订；键和原文不写日志。

已采用推进说明从工作区读取。离线时可查看／编辑／清除说明和使用本地排期。已有有效建议可转为明确标注的手工草稿后采用；服务关闭或上下文变化时先显示来源及变化，不把旧建议冒充新生成。

## 6A. 执行事实与顺延统计契约（核心交付）

本节在读取侧替代旧 `activityInsight()` 的含混口径。不重写已保存的 `rolled_over` 事件名，不删除历史、不修改自动顺延政策、不把有效次数当作工作量。统计按业务规则版本计算，并能在 UI 与 AI 之间复核。

### 6A.1 分类：先判断发生了什么，再计数

基础读取数据为：item 当前记录、目标 planning_periods、该 item 的有序 item_events、这些事件所关联 operations 的 source/kind、必要 effects 与 undo_effects。按 itemId、operationId 和 effectIndex 精确关联；缺字段保留 unknown。[C33]—[C36]、[C39]

| 派生类别 | 必要条件（操作当时） | 是否增加“未完成后顺延” |
| --- | --- | --- |
| 未完成后顺延 `carry_after_period` | before 为 todo、未归档／未删除；同一非 Later horizon；from/to 周期可验证且目标更晚；`from.endAt <= event.at` | 是，每次有效位置变化一次；source 另分 user/system/unknown |
| 提前改期 `advance_reschedule` | 同尺度移到较晚周期，但原周期尚未结束；before 为活跃 todo | 否，显示“提前调整安排” |
| 其他安排变化 `placement_change` | 不同尺度、同尺度回移或 Later 进出等真实位置变化 | 否，不把目标下沉到今天视为失败 |
| 非活跃条目的位置调整 | before 已 done/cancelled/archived/deleted | 否，作为历史／整理操作 |
| 撤销／状态／指导／创建等活动 | 依原操作和 effect 解释 | 不直接增加顺延；按各自用途进入明细 |
| 依据不足 | 缺来源周期、不可定位 effect、历史只有 baseline 或操作时间异常 | 不推断；指标设为 unknown/partial 并显示局限 |

不能仅按 event.type 判定。新统计保留两组计数：**当前活跃轮次**和**任务历史有效总计**；右栏压力使用前者，后者在展开信息中查看。每组按 horizon、source 和类别分开。与原操作关联的撤销已生效时，从有效计数中排除；仍保留审计记录。

一个系统批次影响多项任务时，各 item 只累计自己对应的有效位置变化；不能用整个批次任务数作为本项顺延次数。一次从三周前直接移到本周，只增加一次，另可记录跨度但不能展开成三次未兑现。相同回执、重复 query 和重新打开窗口都不新增次数。重复一键移动到同一周期若没有位置变化，不计；同日真有多次有效调整可在明细计多次，但压力判定按 §5.5 对日期／来源周期去重。

“用户操作”只说明请求来源，不证明用户主动承诺执行。模型不得将 `manual=2` 写成“你两次承诺了但没做”。

### 6A.2 时间：创建年龄、当前轮次与状态占用必须分开

| 指标 | 定义与可用前提 | 展示规则 |
| --- | --- | --- |
| `createdAt` / `createdAgeDays` | 来自可信 item.createdAt；按工作区本地日期差计算，不从第一条 activity 推测 | “创建于……”／“创建已 N 天”；单独不足以触发压力 |
| `currentEpisode` | 当前连续活跃 todo 区间：从创建、重开、解除归档或还原后实际进入活跃 todo 开始；完成／取消／归档／删除结束。撤销造成的真实状态转换也参与 | 当前不活跃则 null，历史轮次可查看；未来排期和 Later 不因此获得催办等级 |
| `currentPlacement` | 当前实际 horizon/period；`enteredAt` 是最后进入该位置的真实操作时刻。`eligibleSince=max(enteredAt, period.startAt)`；未来周期尚未开始时为空 | 只有正处当前周期且活跃时可写“本期安排已 N 天”；停在过期周期写“仍在往期”，不把过期 period 称本期 |
| `plannedOpenSecondsByHorizon` | 按真实状态区间累计：todo、未归档／未删除、非 Later，且目标周期已经开始；过期仍未完成的区间继续计入，不是工时 | “在『本周』列累计待办约 N 天”；不再只写“This week N days” |
| `deadlineNow` | 当前活跃任务有明确 dueDate 且 dueDate < workspaceToday；按本地日期差 | “超过截止日期 N 天”；到期日当天不是逾期 |

年龄、当前轮次的“天”采用本地日期差，不用服务器 UTC 日期。累计状态区间保留实际秒数：不足一天可按小时显示，较大值可显示“约 N 天”；浮层解释其为状态持续时长而非工作时长。两种时间口径分别命名，不互相拼成一个“Open”。DST 测试分别检查本地日期差与真实秒数，不把 23/25 小时的一天误当数据异常。

Later 停留可在历史中查看，但不计入已排期未完成时长，不作为催办证据。未来周期提前创建的等待阶段也不计入该时长。完成／取消／归档／删除后不继续增加未完成占用；重新激活另起轮次。当前 dueDate 不代表历史 dueDate；在既有正文／期限 edit 没有相应历史记录时，不计算“期限修改次数”或过去的精确逾期天数。

基线／导入数据：item.createdAt 可信时仍可显示创建日期，但不代表创建以来的状态历史完整。最早 baseline 之前的状态时长及当前轮次起点可能未知，此时返回 null 或明确的“从某日以来可确认的部分”，不得将最早事件冒充创建日，也不得把 partial 数值包装成精确总计。

### 6A.3 撤销：有效次数与实际时间使用两种投影

**有效次数投影**：按原 item 及位置 effect 判断截至查询时是否被成功撤销；失败／冲突的 undo 不改变计数。不能因同一 operation 中某个 effect 被撤销，就把整批所有任务的记录排除。必要时将 undo marker 关联到 undo operation 的实际时间和顺序。

活动证据的 effective 同样按事件所属 effect 判断，覆盖创建、状态、归档、删除／还原和说明。完成后撤销，原完成记录必须显示“已撤销”；撤销前的历史 cutoff 仍显示当时有效。真实状态区间继续保留原完成与实际撤销事件。

**实际状态时间投影**：按 event.seq 和事务内 eventIndex 还原实际生效区间，包含撤销时的真实 after 状态；同一事务内零时长的中间事件合并处理。不能先删除原操作和 undo 再计算停留时间。例如 10/1 移入本周、10/3 撤销：有效移动可不计，但这两天曾处于该状态的事实仍保留。

这不是“心理负债”算法：时长只描述记录中的状态。撤销完成导致 todo 重新出现时，显示新的当前轮次，并保留先前 done 区间；不能抹去真实中断，也不能把一次取消 undo 算作新的顺延。本文不引入新的 undo/redo 能力，仅消费已提交的效果。

历史回顾的截止时刻必须冻结：只有 cutoff 之前的事件与当时已生效的撤销影响当期计数；不能让今天的撤销追溯删除上周末已经发生的事实。来源不足以重建时返回 unknown，不用当前有效 mask 代替历史 mask。

### 6A.4 不完整记录、时间异常与证据

输出包含 `calculationVersion / asOf / timezone / coverage`，每项重要指标附 quality（complete/partial/unknown/anomalous）和可定位证据。`coverage` 说明 earliestKnownAt、是否存在 baseline、是否达到扫描上限、是否缺操作／周期元数据；不得用一个“置信度 90%”替代缺失说明。

输入按 seq 保持顺序；操作时钟倒退或时间戳与当前观测不一致时，尽可能保留可靠次数，但相关时长标 anomalous，不靠 clamp 到零掩盖。使用 main 注入的业务时钟及工作区时区；界面日期刷新不得凭浏览器本地 Date 自行重算另一份事实。

摘要每个可说明的数字至少能定位到其来源查询／事件范围。UI 可点开本地明细；发送给 AI 时仅附有限证据摘要。**未完成、未编辑、没有应用记录都不等于没有实际推进。**本版不提供“多少天没有工作”“停滞概率”或因创建年龄推断的心理原因。

### 6A.5 共用 DTO 与查询接口

下列为拟新增结构示意，需严格 schema；实际命名可按模块边界调整，语义不能省略：

```ts
type FactQuality = 'complete' | 'partial' | 'unknown' | 'anomalous'
type Fact<T> = {
  value: T | null
  quality: FactQuality
  reason: string | null
}
type PlanningHorizon = 'year' | 'half' | 'cycle' | 'month' | 'week' | 'day'
type SourceCounts = { user: number; system: number; unknown: number }
type CountBreakdown = {
  total: number
  bySource: SourceCounts
  byHorizon: Record<PlanningHorizon, SourceCounts>
}
type PressureWindow = {
  startLocalDate: string          // Inclusive calendar boundary.
  endLocalDateExclusive: string  // Events are also bounded by asOf.
  distinctSourcePeriods: number
  distinctOperationDates: number
  thresholdMet: boolean
}
type ExecutionPressure = {
  level: Fact<'normal' | 'carryover' | 'reconfirm' | 'overdue'>
  windows: {
    day: Fact<PressureWindow>
    week: Fact<PressureWindow>
  }
  suppression: Fact<{
    guidanceBoundary: {
      eventSeq: number
      at: string
    } | null
    hasNewSourcePeriod: boolean
    reconfirmationSuppressed: boolean
  }>
}
type ExecutionFacts = {
  calculationVersion: 1
  itemId: string
  generation: string
  asOf: string
  timezone: string
  sourceRevision: string // Relevant item, undo, placement, state, deadline and guidance dependencies.
  coverage: {
    quality: FactQuality
    earliestKnownAt: string | null
    reasons: string[]
  }
  current: {
    status: 'todo' | 'done' | 'cancelled'
    horizon: 'later' | PlanningHorizon
    periodId: string | null
    dueDate: string | null
    archived: boolean
    deleted: boolean
  }
  createdAt: Fact<string>
  createdAgeDays: Fact<number>
  currentEpisode: Fact<{
    since: string
    elapsedCalendarDays: number
  }> // Inactive: null/complete. Unknown episode start: null/unknown.
  currentPlacement: Fact<{
    enteredAt: string
    eligibleSince: string | null
  }>
  carryovers: {
    currentEpisode: Fact<CountBreakdown>
    lifetime: Fact<CountBreakdown>
  }
  scheduleChanges: {
    advanceReschedule: Fact<CountBreakdown>
    otherPlacementChanges: Fact<number> // Includes Later changes outside PlanningHorizon.
  }
  placementDurations: Record<PlanningHorizon, Fact<number>> // Actual scheduled todo seconds.
  deadlineNow: Fact<{ overdueDays: number }> // Not overdue: null/complete.
  pressure: ExecutionPressure
  evidence: {
    eventId: string
    operationId: string
    category: 'carry_after_period' | 'advance_reschedule' | 'placement_change' | 'state' | 'guidance' | 'other'
    source: 'user' | 'system' | 'unknown'
    at: string
    effective: boolean | null
    fromPeriodId: string | null
    toPeriodId: string | null
  }[] // At most six; attach locally resolved period ranges before generating text.
}
```

上述为拟新增类型，落地须配套 strict Zod、有限枚举、非负数、时间/ID校验及长度限制。精确计数必须满足 bySource 和 byHorizon 汇总一致；字段未知以 value=null 加 quality 表达，不能填零。发送 AI 前对已知周期补充有界的实际起止日期，不扩展成全量事件。

`pressure` 由同一权威查询按 §5.5 计算，不接受 renderer 或模型修改。`windows` 返回日／周两份固定大小的窗口聚合，`thresholdMet` 同时检查来源周期数和操作日期数；它们不等于全轮次顺延总数。`suppression` 返回本次采用的指导确认边界、其后是否出现新的有效顺延来源周期，以及是否抑制重新确认提示；`guidanceBoundary=null` 且 quality=complete 表示没有适用边界，不能用它表示未知。界面直接使用 `level` 展示层级，用这些依据解释原因；最多六条 `evidence` 只作示例与明细定位，截断或更换证据样本不能改变压力结果，也不能要求 renderer 补拉历史来计算等级。

压力各字段独立标注 quality；只有决定该等级所需的窗口、当前轮次、有效撤销与指导边界均有充分依据时，`level` 才能标 complete。依据不足时返回 null 和相应质量，不补零、不猜等级。已独立确认的真实截止风险仍可返回 `overdue/complete`，不受历史缺失或提示抑制影响；生命周期禁用压力的规则仍优先。所有压力依据与摘要共享 generation/itemId/sourceRevision/asOf/calculationVersion，并可通过该快照及窗口／事件序列定位本地明细。

新增有界只读查询：`executionSummary`（单任务摘要）、`activityMonth`（月份事件计数与日期导航）、`activityDay`（单日分页）、必要时复用/扩展 `activity`（全部活动分页）。每次请求绑定 generation/itemId，返回 asOf 与快照修订；按月／日查询携带选择身份，迟到结果不能覆盖另一项任务或另一个月份。cursor 由程序给出，并冻结上界 seq／cutoff；分页遇数据修订时保留一致快照或明确要求刷新，不能静默混合两个版本。

`executionSummary` 由 storage/workspace 查询装配，纯计算放在 `src/domain/execution-facts.ts`；不从 main 反向 import renderer 工具。UI 和 assistance-context 使用同一计算与同一口径版本；复盘传入确定的历史 cutoff。网络不进入 worker 查询或事务。

### 6A.6 有界读取与缓存

只按当前 item 的索引读取事件并关联所需操作／周期；不得扫描全库正文或先把所有历史传到 renderer 再分页。第一版单次统计扫描预算建议 5,000 条相关 item_events，关联 effects 也设置明确上限；超限仅对能可靠证明的字段返回 complete，其余标 partial/unknown。**只读到一段事件、没读到可能的撤销时，不能把该段计数称精确总计或可靠下界。**实现前用 B11-32 的负载测试校准预算，不能删除上限来伪装完整。

worker 可以从一致只读快照流式计算当前任务，UI 只拿有界 DTO；月度导航与单日明细一次最多 100 条，下一页必须使用返回 cursor。空闲和滚动时不全量重算。现有全局 revision 可以触发廉价的本项依赖探测，相关状态／位置／事件／undo／期限／指导及日历依赖变化才使对应缓存失效。

缓存保留有界的已结束区间累计、当前尚未结束的活跃状态区间、周期边界及压力窗口计算依据；这些是查询缓存，不是另一份持久统计真值。仅时钟变化时，使用 main 注入的时钟、工作区 timezone/weekStart 和同一 domain 计算器，从缓存重投影**全部时间依赖字段**：创建年龄、当前轮次日期差、当前安排的未来／本期／往期归属与 `eligibleSince`、`placementDurations` 的开放区间累计、截止风险及滚动压力窗口。开放区间从活跃状态起点、进入当前位置时刻与 period.startAt 中的最晚者开始累计，未来等待不计入；已结束区间不随时钟重复累加。renderer 不另算一份时长或压力。

沿用现有日期／可见视图刷新机制，在跨业务日期、相关周期边界、唤醒或重新获焦时更新当前投影；时间显示刷新也走同一计算器，不新增后台轮询。例：周日晚打开一项下周手动排期任务，保持详情至周一且没有任何业务写入，`eligibleSince` 应在周期开始时生效，待办秒数只从该边界开始增长；压力事件离开窗口后也要重评。缓存输入足够时不重新扫描历史；不足或失效时只做有界补读并按字段降级，不能沿用已过期的完整等级。

会话输入缓存绑定 generation、itemId、相关依赖、timezone/weekStart、calculationVersion，以及查询模式（当前／历史）、构造输入时的基准 cutoff 和事件 seq 上界；派生结果另绑定目标 asOf/cutoff，工作区替换时全部清空。当前视图只在依赖未变时从缓存基准向前重投影，生成新的 asOf 快照。历史查询按指定 cutoff 独立构造和隔离输入，不能把较晚的累计值裁剪成过去事实；固定历史 cutoff 不随当前时钟变化。时钟回拨早于缓存基准时不得继续使用较晚聚合，应标记相关时间异常并按有界规则重新读取／降级。UI 和 AI 对同一快照使用同一投影，不能分别写两套算法；仅时钟刷新不改变 sourceRevision、item.version 或 workspace.revision。初版不持久化一个可漂移的统计总数表；精确历史仍以原记录为依据。此统计增量不单独要求 schema v9：§7 的 v8 成本来自推进说明/新 effect，现有统计先读取可用 v7 事实。

加载失败显示错误与重试；如保留上一次同任务结果，明确标记“尚未更新”，不能展示为已同步的风险或送入新 AI 请求。切换任务立即移除旧数字；只读访问不创建 planning_period、不触发人为操作、不改变 item.version 或 workspace.revision。

### 6A.7 AI 使用与安全落点

新增结构化 `executionFacts` 投影，不能把任意 AI 文案塞进旧 signal.detail 后当权威统计。卡点上下文最多附 6 条相关活动摘要，包含已知来源、真实原／目标周期、发生时间、有效／撤销标记和缺失限制；既有预算超限时裁剪明细，不伪造精确总计。summary、pressure 与 evidence 应由同一快照产生，模型不得用证据样本重算压力等级。

统计支持提出有依据的问题，不支持自动诊断。“系统自动顺延一次”只能作为任务仍在安排中的信号；不转译成“你拒绝一次”“你没有自律”。模型不得把采用方案、改标题、移动任务或编辑说明当成实际完成工作。压力文案与阈值由本地规则生成，AI 只在明确请求时生成推进建议。

本版 waiting_note 仍为纯文字；没有复查调度时不得在 DTO 中伪装一个已激活的 waitingUntil/nextReminderAt。起草／复盘若加入新统计发送范围，同样检查相关 purpose consent；没有同意时沿用原允许的数据投影，不影响本地数字，也不悄悄扩大后台发送。

新增请求的 context 依赖包括事实快照与 calculationVersion；相关状态改变、跨业务日期导致风险变化后需更新预览，保留用户草稿。无关任务变化不应让当前采用无条件失效。统计刷新、提示出现和求助窗口打开均不写工作区；只有 §7 的明确采用才产生 guidance 事件。

## 7. 持久化、写入、撤销与历史

### 7.1 为什么不直接拼进 description

基线普通 edit 不产生文本撤销 effect；直接替换或附加说明会与 Lexical autosave、用户后来编辑、原始 Markdown 保真发生冲突。[C09]、[C14] 本文选择独立、可选的推进记录来明确字段归属。它不是新的用户功能模块，也不要求普通任务创建该记录。

新增 `item_guidance` 表，`itemId` 作为 PK/FK；保存 revision、可空的严格 JSON value、updatedAt 和关联 operationId。清除保留 tombstone，避免“删除后又重建”被旧 revision 误判。草稿与模型结果不进入此表。

Store 提供独立读取／写入；普通 edit 只更新既有字段，不能因 ItemDetail DTO 扩展而顺带重写 guidance。对 Item.version / Workspace.revision 的更新走既有 touch／transaction，guidance revision 另行单调递增。

### 7.2 新增受限命令

新增 `applyAssistance`。只支持当前 item 的推进说明 set/clear，以及可选的一次 move。没有 create、删除、改标题、改 dueDate、任意关系变更能力。

命令封套沿用 operationId / generation；包括 expectedVersion、expectedGuidanceRevision、必要时 expectedPlacementVersion。guidance 用显式 `keep / set / clear` 判别，避免 optional 与 null 含义混淆。

AI 采用附带由应用准备的依赖版本／目标周期 guards；这些 guards 不由模型生成。纯手工编辑不要求有效的模型 ticket，但依然受字段、代次、生命周期和版本约束。

写入步骤必须在同一 Repository 事务内完成：

1. 按既有规则校验 generation、operationId 与 requestHash；重复且相同请求返回原回执，不重放。
2. 检查 setup、maintenance、待恢复状态、目标 item、推进记录版本和必要依赖。
3. 检查 AI 预览依赖仍有效；仅无关任务变化不应因整个 workspace revision 变化而失败。依赖任务／周期变更则要求重看预览。
4. 对移动复用现有目标周期计算、placement 版本、Later 解除父关联与排序规则；不递归调用 `Repository.execute`。
5. 写入推进记录与可选移动，添加相应 effects 和事件；任何一步失败全部回滚。
6. 保存唯一回执，changed=false 不新增撤销或成功提示；返回后按既有 prepared write 链刷新。

renderer 用 `PreparedWrite` 预留写槽位，再读取权威版本。不能先拿旧版本后排队，也不能自动把用户已看过的变更换成不同目标日期。

### 7.3 未知回执与重复提交

确认提交后暂时失联时保留原 command 与 operationId，先 `getReceipt`，确认确未提交才用同一操作重试。不得通过生成新 operationId 来绕过未知结果。重复按钮、窗口关闭重开、迟到回复不能造成第二份采用记录或第二次移动。

当 operationId 相同而 payload 不同，返回冲突。用户编辑了待确认内容，应先解决旧回执，再开始一个新操作。

### 7.4 撤销 effect

新增 v2 effect：`guidance`，保存该记录的前后有效内容及必要身份守卫；正文有界，不包含完整任务描述或模型会话。原有 v1 effect 的结构不变，新操作按实际 effect 类型标记版本，旧回执保留版本 1。

撤销推进说明仅比较本操作拥有的 guidance 内容／身份；用户后来改标题、期限、颜色等无关字段不应使其失败。当前 guidance 被另一操作编辑，则明确冲突，不覆盖新值。版本保持递增，不回滚行版本或改写历史回执。

复合“说明＋移动”沿用现有 savepoint 原子撤销；任一 owned effect 冲突，整次不改数据，使用既有 conflict_skipped 反馈和会话处理。不要只撤回说明而把原移动留下。

导入时同样要求 `applyAssistance` 的全部原 effects 都由同一个 `undo` 覆盖，包括移入 Later 的父关联解除；拒绝仅逆转说明、移动或关联的局部标记。历史指导校验按 operation/item 索引取 effect，不为每条事件扫描完整批次。

单独说明撤销不改变完成／取消状态；若任务后来完成，允许撤销说明且保持完成事实。删除状态需要先按既有规则恢复条目，不能通过撤销说明隐式复活。包含移动时继续遵守原位置、关系与过期周期 hold 守卫。

手工修改／清除已保存推进说明使用同一新命令，进入同一会话撤销栈；原有标题／正文编辑的文本 undo 语义不改。

### 7.5 历史和导出

为采用／编辑／清除写入有序的 guidance 事件，并关联不可变 operation。活动列表只显示操作名和时间，不默认展开求助内容；§6A 的分类器识别这些事件，但不增加顺延次数或实际完成次数。周期回顾用事件 seq／操作顺序解决同时间戳先后，不能只比较文本 updatedAt。

新 dataset 包含所有 guidance heads（包括 tombstone）、相关 operation/effect 与事件。JSON 导出和 SQLite 备份／恢复都必须保留；不能只备份当前说明却丢失可解释的历史。

### 7.6 生命周期连带规则

| 操作 | 推进说明行为 |
| --- | --- |
| 完成／取消／归档 | 保留记录，只读；不自动删除或生成提醒 |
| 删除与还原 | 随 item 保留、隐藏并恢复；不跨 item 复制 |
| 清除推进说明 | value=null，递增 revision；支持撤销 |
| 普通移动／自动顺延 | 原记录保留；带有旧日期的文字不自动改写，显示记录更新时间 |
| 原任务说明 autosave | 不改 guidance；返回快照不得重置编辑器 selection/history |
| 整库恢复／重置 | 代次更新，旧会话／ticket／pending AI 结果全部失效 |
| 空标题关闭 | 有有效 guidance 时不是“空任务”，必须阻止 discardEmpty |

### 7.7 数据升级：显式、可回退，不静默原地迁移

建议 schema v8；新 DDL 包含 guidance 表和 v1/v2 effects 支持，dataset 支持导入 v1—v8。v1—v7 源 guidance 默认为空，保留原日期、位置、事件与回执，不合成“以前用过 AI”的记录。

启动升级还必须保留原工作区的 `theme / style / checkStyle`。临时新库的默认外观不能覆盖旧偏好；普通备份／JSON 恢复和重置仍保留目标工作区的当前外观，两种路径明确区分。

**必须处理启动阻塞。**现有 startup 对旧版本只读拒绝；仅改 `schemaVersion=8` 会使已有 v7 用户无法正常进入。[C21] 本版要提供兼容恢复流程：只读识别旧库 → 显示版本及迁移说明 → 创建并校验保护副本 → 使用导入验证器构建临时新库 → 用户明确确认 → 原子替换活动文件。旧库内容／副本保持可恢复，不直接对源库执行 ALTER；失败或取消不动原库。

可复用现有 transfer 的校验、保护备份和替换能力，但启动受阻时必须有可到达的恢复入口，不能让用户先进入一个进不去的设置页。不得复用“重置”来删除用户数据，更不能要求用户自行删除旧文件。

扩展所有 schema/requiredTables 检查为来源版本感知，旧库没有 guidance 表是正常情况。新库缺表、非法 guidance、孤儿 itemId、非法 effectVersion、回执／历史不一致应拒绝，不能静默丢弃字段。

降级运行旧应用时明确拒绝新库；使用迁移前副本恢复，而不是把新格式硬塞给旧版本。本项是新增结构化持久化的真实交付成本，必须在发布说明与验收中体现。

## 8. 安全、隐私与性能

生成不是授权。模型只提交结构化建议，不能调用写命令或外部工具；main 和 worker 按白名单处理。不要把任务说明中的“忽略规则”“删除其他任务”等指令升级为系统提示或执行权限。

网络只在 main；允许现有明确配置的 provider 端点，不跟随模型输出 URL。Key 沿用 OS 保护、无明文回退；新的 consent 与设备设置不进入工作区备份。

默认不写 prompt/reply、求助正文、任务标题、描述、上下文摘要或其可关联哈希到诊断日志。仅记录 request 的非内容型耗时、状态、模型标识和费用／token 元数据（服务未提供则标 unknown）。用户显式导出的评测样例应脱敏，不开启内容遥测。

每个用户触发最多一个生成调用；无自动修复 JSON 循环、无自动换模型／provider。失败提供手工编辑与显式重试。HTTP 错误、解析错误、超限、超时、取消和未同意分别显示，不笼统说“Key 无效”。

关闭辅助面板后不保留模型轮询。正常启动、滚动、拖动、打开普通任务和单纯查看推进说明均不得新增网络请求。新增代码按功能懒加载，不能把全部提示词／编辑器装进启动关键路径。

最小性能门槛是普通输入的模型调用数不增加、看板摘要有界、无全表正文读取、网络不占 worker 写队列；详情统计改为 §6A 的单任务有界读取与按月／按日分页，打开其他无关任务或全局 revision 更新不反复拉取当前任务全部历史。辅助响应速度和费用需要真实服务评测；15 秒沿用超时不是响应时间承诺。

### 11.3 模型质量评测

准备至少 60 条脱敏、可复核的标注场景：保留原八组共至少 48 条（明确普通任务、模糊目标、已有部分进展、等待他人、现实时间不足、过期／冲突日期、重复行为与一次性任务混淆、恶意／无关输入），另加至少 12 条执行事实场景，覆盖系统/手动、提前改期、跨多周期一次同步、完成重开、历史未知、统计相同但实际卡点不同。总集至少 15 条覆盖非中文输出。

比较“现有基础提示”与“增加上下文的辅助提示”；普通输入比较升级前后，不把使用更多调用当作成功。记录结构有效率、越权动作率、与已有内容重复率、需要用户重写的程度、调用数、延迟和实际可得费用；新增“无依据的拖延/心理归因”“UI 与 AI 数字不一致”“把未记录视为未工作”检查。未提供 token／价格时标 unknown，不反推虚假数字。

推荐发布门槛：所有确定性越权／越界用例被程序拦截；固定合法响应夹具全部正确应用；至少 90% 的质量样例经人工评审为相关且无需大改。90% 是本产品建议门槛，非现有实测结果。任何会覆盖用户正文、跨任务写入、伪造执行或越过同意范围的问题均阻塞发布。

模型评测需要网络与计费授权；本文仅安排任务，未执行。不得用合成模型结果替代真实质量验收，也不得用真实模型偶然成功替代确定性契约测试。

## 13. 体验变化与主要风险

| 项目 | 升级 | 代价／风险及约束 |
| --- | --- | --- |
| 普通任务 | 不增加填写负担，保持原主路径 | 新入口不能常驻挤占空间；需回归快捷键与焦点 |
| 求助 | 当前任务上下文直接进入建议，不必复制到聊天软件 | 新网络请求只在明确触发后发生；效果需评测 |
| 采用建议 | 可以真正留下可继续的说明和清楚的安排 | 新事务／元数据／撤销不是“加 prompt”规模 |
| 数据安全 | 不覆盖原 Markdown；精准保护后续编辑 | schema v8 需要显式升级／恢复与旧库保护，用户有一次操作成本 |
| 隐私 | 有界上下文、按服务确认、新内容不写诊断 | 发送内容比既有标题型起草更丰富，不能继承旧同意当作扩权 |
| 复盘 | 能理解当时采用过的推进方式 | 历史时间边界复杂；缺记录必须写 unknown |
| 模型组合 | 按需分工，不增加普通输入生成请求 | 没有事实证明双模型必定更好；需同样例对比 |
| 习惯 | 保留自然接入方向，无插件包装 | 核心版只提供方法建议，不能宣传完整习惯追踪 |
| 执行统计 | UI/AI 同口径，区分提前改期、未完成后顺延、来源及真实状态时间 | 数字会与旧算法不同；发布说明解释口径变化，不把更正当数据丢失 |
| 适度压力 | 真实安排差距与期限可见，并有卡点帮助出口 | 阈值是产品假设；需检查用户回避/频繁无意义重排等副作用，不承诺完成率提升 |
| 活动月历 | 保留现有视觉位置，按日可追溯、多事件不覆盖、完整历史可分页 | 增加查询/撤销时间投影与无障碍测试，但不扩大主看板 |
| 统计性能 | 替换 renderer 反复全量读历史，有界查询和按项依赖缓存 | 预算不足的精确总计需 unknown；不能用删上限换取表面完整 |

本版发布阻塞：跨代次或跨任务写入、正文被覆盖、原数据无法恢复、复合操作半提交／半撤销、未同意发送私人内容、把未实现能力伪装成已启用；以及把自动同步跨度虚构为多次失败、完成后未完成时长继续增长、UI/AI事实不一致、跨任务串统计、局部历史伪装精确总计、当前撤销改写历史 cutoff。

本版不使用“任务总完成率”作为唯一成功指标。分别观察：建议是否被采用、是否需要重写、用户是否报告下一步更清楚、合理调整／等待／取消的结果，以及核心任务真实完成情况。默认不收集内容遥测；验证先用脱敏样例和负责人测试记录。新增压力体验分别观察用户是否理解数字、能否找到下一步，以及是否因警告回避详情或为了清零而无意义改期/取消；不把“顺延数变少”直接当真实生产力提升。

## 附录 H. 习惯真实执行的后续接入契约

**本附录不是插件方案，也不是本次核心交付的暗中必选项。**其作用是保留前面讨论的完整产品方向，并明确未来从“习惯方法建议”升级为“真实习惯能力”的门槛。若决定与核心同版交付，以下 H-TODO 全部转为必做，并扩展相应 schema／验收；不能只隐藏未完成按钮就声称已经实现。

### H.1 用户体验

无需全局习惯开关，也不改变普通新建。用户从目标中明确选择“建立持续行动”，或在智能建议中主动采用习惯方案，才展开习惯专属字段。已建立习惯不依赖 AI 在线；暂停／结束的是某项习惯，而不是整个智能服务。

区分三个对象：目标结果、持续规则、某次执行。比如“今年读完十二本书”是结果，“选定的晚上读书”是持续规则，“今天完成本次阅读”是执行。规则本身不冒充普通父任务；实际执行可与符合周期规则的目标关联，不强制填满所有中间列。

情境提示是可选文字，不是软件自动检测到用户“吃完饭”的事件。起手动作不等于完成标准，AI 建议的频率／时长与用户原话分开，确认后才生效。

### H.2 最小支持范围

先支持每日或指定星期的每日一次执行，不包含“每周任意三次”、多次／天、复杂 RRULE、地点触发、节假日工作日自动推断或事件依赖自动化。固定使用工作区时区；开始日期、结束日期、频率、完成标准、关联目标和可选情境均要有明确值或明确不设。

不实现系统提醒时就不出现“提醒已开启”。主板仍是今天列的一次执行；习惯的规则／历史在该习惯详情内管理，不另设常驻习惯列或热力图。

### H.3 数据与执行规则

需要独立 habit definition、schedule version、occurrence 身份和执行日志。建议逻辑唯一键至少含 `habitId + workspaceLocalDate + slot`（首版 slot 固定 1），防止重启、唤醒、时钟回拨或重复 reconcile 造成同日重复。修改 schedule 不应因版本号改变而生成当天第二次执行。

当前日期按需生成，不预生成全年卡片。几天未打开应用后不批量补出过去待办；规则历史可计算当时的预期机会，但没有记录就是“未记录”，不是确信没做。补记由用户明确选择实际日期，不能伪造应用观察到的完成时间。

基础 item 仍只用 todo/done/cancelled；habit occurrence 的“跳过”由自己的字段表达，不能混用任务取消来代表跳过。一次勾选与 occurrence 日志在同一事务中更新，一次撤销同步还原；没有双向松散同步。

未完成的历史 occurrence 留在原日期，不自动顺延、不进入普通 backlog 统计／批量顺延建议，也不形成不断增长的“欠账”。同版接入时还必须从 §5.5 的普通任务顺延压力、§6A 的普通执行轮次聚合中排除，独立显示完成/跳过/未记录；主功能未实现 habit 时不能靠文本猜类型进行排除。这要求修改所有相关查询与统计，不只是 `canRollover` 一个函数。

删除／跳过当天 occurrence 保留抑制记录，当天 reconcile 不应马上重建它。用户明确“恢复本次”才重新启用。规则删除／暂停不会删除历史，暂停期间不计为应执行机会；重新启用不补发停用期间记录。

修改规则默认从下一工作区日期生效，已生成及历史执行快照保持；用户要修改今天应单独确认。被关联目标完成／取消／归档／删除后暂停未来生成并在详情说明，历史保留；恢复目标不悄悄恢复习惯，用户明确继续或改关联。

### H.4 建议与采用

Jev 可以辅助判断“用户表达了重复意图”，但不能直接判定所有重复都属于习惯。“每月交账单”这样的任务不能自动套用不积欠账的规则。

从明确“添加习惯”入口进入时不再调用 Jev 判断用户是不是要加习惯。DeepSeek 可起草频率／情境建议，但缺少的字段仍需用户确认，不从结果目标推断未经确认的生活安排或健康方案。

采用 habit 必须有新的有限业务命令、预览、幂等、撤销、导出与完整恢复。内部运行能力确认可用前，不把 `create_habit` 加入任何模型 action 集合。

习惯完成率与目标结果进度分开，不自动换算“完成一次＝减重目标前进多少”。不以连续天数归零惩罚中断，不根据打卡次数宣布习惯已经形成。

# Desktop sync

## Apple and Google sign-in acceptance

Both providers use the same Supabase account and encrypted workspace flow. Verified matching emails follow Supabase automatic identity linking; different emails remain separate. No manual identity linking is offered. Authentication never replaces sync-password proof or the bound-user check.

Failure cases recorded before implementation: Apple receives Google-only parameters; a missing/unknown provider reaches OAuth; repeated clicks start two authorizations; cancelling leaves the port or buttons locked; authorization failure is hidden; a late callback restores a cancelled session; changing providers bypasses the bound-user guard; a browser callback reports success before exchange; missing profile names break sign-in; one locale lacks Apple labels; a private key or client secret enters a client build. Native Electron acceptance records `output/tests/apple-login/report.json` and screenshots. Live providers, signed installers and Windows remain separate acceptance.

Desktop installs sign in with the same Apple or Google account, use the same cloud workspace and sync password, and converge encrypted ops. The board stays usable while signed out. Payments, snapshots and QR pairing are not in this client.

The password is an ordinary secret of 8 to 128 characters. Argon2id (`m=8192` KiB, `t=2`, `p=1`, 32-byte output) derives a key that seals a random recovery keypair. Salt and those parameters travel inside the existing recovery envelope. The roster, checkpoint and workspace-key wrap stay as they are. Keys use OS protection when available; the no-Keychain recovery path uses a password-protected local vault. A phrase-era envelope does not open.

The engine lives in `packages/sync` (`SyncRemote`, session, first-connection, join, board, codec). Desktop OAuth and the keychain vault stay in `apps/desktop/src/main/sync`. Mobile native authentication and sync are a separate implementation milestone.

## Sync difference review

The board shows one quiet notice for pending local task differences. View details opens an independent, content-sized dialog. Each step compares read-only Kanban task presentations side by side, with native radios defaulting to the synced result. Selection changes only the radio and outer border. There are no editors, field selectors, task dropdowns, footer instructions or completion summaries. Next confirms one task; Finish confirms the last task and closes. Defer/Escape preserves unresolved differences. Confirmed differences remain confirmed after restart and sign-out/sign-in.

Only lost local user changes need review. Duplicate relationships, redundant state, system rollover/undo guards and rejected operations from other devices do not produce error banners. Concurrent text changes retain canonical sequence ordering. New local ops carry their observed `basisSeq` inside the encrypted payload, so a later canonical op can identify an overwritten local field without flagging a causally later remote edit. Older ops without that metadata still support rejected-operation review. No wall-clock ordering or plaintext cloud metadata is introduced.

Choosing the synced result only acknowledges the listed records. Choosing the local result creates one new operation containing only the lost fields/actions. A deleted task requires the explicit local recovery choice; the current deletion identity is guarded, and no other deleted task or endpoint is restored. Invalid relationships remain visible but unavailable. The authoritative transaction checks generation, owned values, lifecycle and dependencies against the preview token, revalidates the action with the production applier, and commits the new operation, history and acknowledgement together. An unchanged operation ID returns its durable receipt. Stale previews refresh the comparison; failed or unknown writes do not advance without receipt confirmation.

An offline task creation rejected because its parent was deleted remains reviewable, including later offline field edits to that same task. The current side states that the task is absent from the board. The local side previews the same task identity and final local content as an independent task, without invalid links to missing/deleted parents. Only an explicit local choice creates that preview as a new operation. The deleted parent stays deleted; task identities are not regenerated. A dependency change that alters the preview plan invalidates its token before writing.

Acceptance failure cases defined before implementation: selection changes typography or task dimensions; editing controls/extra selectors/footer instructions/summary remain; a short dialog retains large fixed whitespace; selection submits immediately; a new step inherits the local radio; double click or repeated Enter skips a task; default acknowledgement restores a deletion; local recovery restores another deleted endpoint; invalid relationships become writable; unrelated remote edits are overwritten or invalidate a field-only choice; a causally later edit generates a false concurrent warning; a stale lifecycle or workspace generation is accepted; acknowledgement/new writes are not atomic or repeated after an uncertain reply; acknowledged or harmless conflicts return after restart/relogin; multiple records for one task become separate steps; a write failure discards the selection or closes the dialog. Verify production SQLite/encrypted peers and native renderer/preload/IPC, with repeatable reports/screenshots under `output/tests/sync-review/`.

## First connection and returning devices

First connection preserves data by default. A populated local board joins a cloud workspace with no task history automatically; its calendar, task identities, placements, relationships and rollover policies are retained. First upload fills implicit setup defaults and already-applied offline rollover that may be absent from the ordinary outbox, then checks the reconstructed task data before committing. An empty local board downloads the existing cloud board. Independent populated boards show one primary “Merge and start sync” action and keep both sets of tasks. Replacement stays behind a secondary option with explicit acknowledgement. A verified protective backup precedes installation; backup or installation failure leaves the local board intact.

Cloud emptiness means the complete verified operation history contains only initial calendar, policy and preference operations. Zero live tasks is not evidence of first use. Creation, deletion, restore, archive and other business history make the cloud established. Known item identities, including tombstones, are never imported again as new items. A device already bound to that cloud resumes its cursor and pending operations after logout/login, without installing or merging the board again. Repeated join requests are idempotent at the storage transaction boundary.

An initial import carries its source calendar inside the encrypted operation. Calendar adoption is allowed only before task history exists; concurrent initial imports keep the first established calendar and align later imported placements to it. Calendar editing after tasks exist remains locked. No task content or plaintext calendar is added to cloud metadata. Both devices must use a build that understands this import metadata; older strict parsers fail closed.

Acceptance failure cases (defined before implementation): B creates sync while empty, A then joins with tasks and loses a task, ID, relation, status or period; B never receives A's calendar/data; an offline automatic rollover is omitted/rejected during first upload and moves a task back to an expired period, changes its later manual order, or loses a deleted task’s recorded placement; relogin or repeated join creates duplicates or resets pending receipts; a stale local copy recreates a cloud-deleted task; a cloud with zero live tasks is mistaken for first use; concurrent initial imports overwrite the established calendar or lose either board; incorrect passwords, failed downloads, failed protective backups or failed transactions modify local data; both-populated join defaults to replacement; rejoining a restored/paused workspace silently discards changes. Use real SyncService, SDK, SQLite and native renderer/IPC with a controlled encrypted cloud, and save reports/screenshots under `output/tests/sync-join/`.

Preferences and API keys use that same log. A theme, language, shortcut or saved key becomes a `pref.set` op and is sealed with the sync password’s workspace key. The other computer applies it without a restart. The key is stored again in that computer’s keychain. The workspace database keeps a sha256 fingerprint, not the key. Window size, the sync session, the device id and the sync password itself stay on the computer where they were created. Week start is already part of the locked calendar, not a separate preference.

`collapseCompleted` uses the existing encrypted `pref.set` log and renderer settings IPC. Missing/invalid local values default to `false`; untouched defaults are not seeded. Remote application does not echo a local write and waits for active inline edits/drags to end before changing the board projection. It never changes task data, history or undo membership.

## Credential access at startup

Normal app quit, process restart, computer restart and signed upgrades retain the provider session and device keys. Explicit account sign-out disables automatic restoration durably before reporting success. The next sign-in runs fresh Apple/Google authorization and verifies the sync password before enabling automatic restoration again. Local item IDs, workspace pins, cursors, pending sends and tombstones are unchanged. Revoked authentication and deleted credentials still require recovery; temporary network/storage failures preserve data.

macOS uses an application-private Data Protection Keychain item for a random local encryption key. Every query uses `LAContext.interactionNotAllowed`. No user-presence, biometric or iCloud-synchronization requirement is added. Entries use `AfterFirstUnlockThisDeviceOnly`. The production application identifier and access group stay `947MAGH97Q.com.goalloom.desktop`, backed by an embedded macOS Developer ID provisioning profile. Windows retains DPAPI. Neither platform stores a plaintext sync password or an unprotected local decryption key. Existing AI credentials retain their independent noninteractive Safe Storage path.

`sync-session.bin` is authoritative once created. Readable old OS sessions migrate automatically without replacing `sync-vault.bin`. Unreadable old sessions and existing password-only sessions recover through Apple/Google and the sync password, then promote to automatic restoration when secure storage is available. Once the current file exists, stale legacy/password files cannot restore an older session. If current ciphertext is damaged, preserve it and report a storage error. Missing native code or denied access never creates a replacement key during a read.

An unused or saved signed-out session does not access the OS store. Settings/status reads also do not request access. Explicit sign-in may read preserved keys under the same no-dialog policy, but fresh provider authorization alone does not enable automatic restoration: the persisted resume flag stays inactive until password verification/setup succeeds. Cancellation and incorrect passwords keep that flag inactive. A verified existing local password vault can restore its original device keys; otherwise the authenticated account must own the pinned workspace before cloud recovery or device registration. A returning device resumes the existing binding rather than creating a cloud or replacing a board.

The vault stores its public resume flag beside the encrypted bytes in one atomic file replacement. The flag controls automatic access; it is not an authentication/encryption boundary. Keep-local sign-out clears the authoritative flag without cipher access or waiting for network revocation. Serialized writes and a lifecycle check prevent an earlier token save or password-vault promotion from reactivating a completed sign-out. A failed flag write reports a storage error and retains the previous runtime state. Sign-out disposes local refresh/subscription state and attempts this session's revocation in the background. Other devices remain signed in. An inactive legacy vault remains inactive during migration.

When the OS store is unavailable, the password-protected fallback still permits Apple/Google authorization and sync without a system dialog. This exceptional mode requires provider authorization and the sync password after a full app quit, and the five-language notice explains that limitation. After successful password proof and a protected-session write, the notice disappears and later starts restore automatically. Temporary denial of an existing automatic session preserves its ciphertext and retries silently on wake/connectivity restoration. Password-only files never become an unprotected automatic-login fallback.

`sync-password.bin` uses bounded Argon2id parameters to wrap the stable recovery key; HKDF-separated AES-256-GCM protects the key wrap and credential body with fresh nonces and account/workspace-associated data. Only identifiers/KDF parameters are public. Writes use private permissions and atomic rename. If another device changed the password, verified cloud recovery can open the existing body with the recovery key and restore the original device. An unreadable legacy vault can require a recovery device registration, while retaining the workspace pin, cursor and outbox. Interrupted creation keeps its saved identity and keys; retries do not upload before the draft is durable.

Prepared sends use stable recovery-key protection in `sync-send-v2-*.bin`, scoped to account/workspace/local generation. That key survives password changes and workspace-key rotation; a device without recovery material uses its stable device key. Legacy OS journals remain untouched when unavailable. Complete task payloads can be recovered from SQLite with their original IDs/hashes. Unknown legacy sends containing redacted API keys wait for their original payload or remote replay and never substitute a different key. This does not block task downloads. Incoming AI keys that cannot enter the independent OS store remain encrypted inside the credential vault for later delivery, outside task databases/backups.

Packaged identity and data paths remain `Goalloom`, `com.goalloom.desktop` and the existing `Goalloom` directory. Source development uses `Goalloom Development`, `com.goalloom.desktop.development` and its separate directory. Explicit isolated profiles remain supported. Unprovisioned source/ad-hoc apps cannot establish native Data Protection acceptance. The app never changes historical ACLs, erases unreadable secrets or opens a system authorization/unlock dialog to repair old entries.

Acceptance failure cases, defined before implementation:

- Unused/signed-out startup accesses credentials; restart or a same-identity upgrade loses a session; a late save reactivates sign-out; a failed flag write falsely succeeds; cancellation or incorrect passwords allow automatic restoration.
- Case 1 loses tasks/calendar/IDs; repeated login imports twice or resurrects a deletion; a zero-live-task cloud is mistaken for first use; unknown sends lose their original identity/hash; another account receives a kept board.
- Recovery fails to promote to automatic restoration; migration overwrites old ciphertext; a read creates a replacement key; missing/incorrect provisioning or a locked/untrusted store opens UI; a missing native module prevents local work.
- Offline startup requires manual login after connectivity returns; a password changed elsewhere loses pending work; unavailable AI storage blocks task synchronization; clear-local leaves a restorable session.

Production service/SDK/SQLite tests cover these journeys with isolated peers and a controlled encrypted cloud. Native renderer/IPC tests cover login/logout and five-language feedback with synthetic credentials. `test:keychain-native` uses private disposable legacy keychains and checks silent rejection of an unprovisioned Data Protection caller. The hosted Developer ID gate checks a real private session key across full process restart and replacement by a new signed bundle version, plus previous-version Safe Storage restoration. No test edits user credential ACLs/search lists. Source/synthetic/ad-hoc evidence is not signed installer, physical reboot, live Google or Windows acceptance. Reports live under `output/tests/sync-security/`, `credentials/`, `keychain-native/` and `keychain-signed/`.

## Sign-out and local cleanup

Settings opens a confirmation dialog. Keep local tasks is selected by default. Cancel, Escape and the close button leave the session unchanged and return focus to the sign-out button. Keeping tasks preserves offline editing, device keys and pending receipts; a later sign-in must use the bound account. A different Supabase user is rejected before device setup, cloud creation or upload. Explicitly resetting the local workspace creates an unbound generation.

Clear local tasks is an explicit destructive choice. It discards pending local changes and removes the task database, history, internal backups, legacy/current OS sessions, password vaults and prepared-send files. It leaves cloud workspaces, separately saved AI credentials and device preferences intact. User-created exports or copies outside the managed profile are outside this operation. The random profile wrapping key contains no account/session data and can remain in OS storage after all local ciphertext is removed. The dialog states this scope. Cleanup requires an unlocked OS or password vault. Merely completing Google authorization does not authorize erasing an unreadable vault.

The storage queue drains accepted writes. A verified empty database is prepared before the open connection closes. A private staging directory and atomic handoff receipt protect the file replacement. An interrupted, uncommitted handoff restores the original files before SQLite opens. A committed handoff finishes deletion before startup can proceed. A pre-commit file/open/rename failure restores the previous board and session. If a platform blocks deletion after commit, the board stays empty and signed out, displays a specific cleanup error, and blocks further sign-in until the remaining files are removed. Reversing a partially completed destructive deletion would be unsafe.

Successful cleanup creates a fresh database file and generation, invalidates old writes/session undo/drafts, releases pending assistance/link requests and shows first-run setup. A different account can then download only its own cloud board. It does not silently reuse the cleared account's data or keys. This is separate from protected Reset workspace, which retains its backups and confirmation rules.

## Forgotten sync password

Settings shows only “Change password” while the device is ready. It opens a native dialog with the new password and its confirmation; the existing action does not ask for the old password. “Forgot password?” is available at password entry, in Settings and first-run setup. Recovery opens one native dialog with a flat form, other-device guidance and the new-workspace path. The destructive alternative replaces that dialog's content with its warning, new password and exact deletion phrase; Back returns to the recommended path. No cards or additional dialogs are nested inside the recovery dialog. Cancel/Escape returns focus to its entry; an in-flight write blocks dismissal. Errors remain visible inside the active dialog and retain the draft.

UI failure cases recorded before implementation: ready exposes both password actions; an entry still has an ellipsis; fields expand inside Settings; recovery nests cards or a second dialog; destructive navigation submits the recommended form or clears typed passwords; an incorrect or differently cased deletion phrase enables submission; Cancel/Escape closes Settings or performs a sync action; an in-flight request can be submitted twice or dismissed; a failed request hides its error behind the dialog or loses the draft; a locale clips controls; first-run recovery bypasses explicit calendar confirmation. Extend the existing native sync-security journey and retain reports/screenshots under `output/tests/sync-security/`.

Recovery has three paths:

1. If another device still syncs, change the sync password in Settings on that unlocked device, then use that password here.
2. **Create a new cloud workspace** is selected by default. Set and confirm a new password. The app protects the local board, creates a fresh workspace/key/recovery proof and uploads this computer's current tasks. It does not delete old cloud operations, envelopes, rosters or checkpoints. No destructive phrase is required.
3. **Reset cloud and re-upload** is the dangerous last resort. Type `DELETE ALL CLOUD DATA` exactly. The IPC schema also requires that phrase. This deletes the explicitly selected workspace and interrupts every device still using it. Other preserved workspaces remain intact. A verified local protective copy precedes this RPC.

Cancel returns to password entry. If the password is remembered later, it can still open the preserved old workspace on a device bound to it. Initial recovery on an unconfigured local board first completes explicit calendar/setup confirmation; it never creates tasks or uploads a baseline before that confirmation.

A recovery draft persists new workspace identity and keys inside the encrypted vault before creation. Lost responses reuse that identity after restart. Existing keys remain usable until cloud creation succeeds. Once new keys are selected, exchange stays paused until the current local board is atomically rebaselined and bound. A failed protective copy leaves cloud and local data unchanged. Installation failure keeps the board and draft for retry, without uploading an old send journal under a new cloud key.

## Multiple workspaces

An account can retain several encrypted cloud workspaces. Newly signed-in devices without a saved binding discover the newest workspace (`created_at`, then UUID, descending). Returning devices query their saved workspace ID explicitly and stay there, even when another device creates a new one. A missing or foreign pinned workspace fails closed; it never falls through to a different workspace.

Preserved spaces may be inaccessible on a device that lost the password, but their encrypted data remains and existing devices can keep syncing. Creating a new space does not revoke an old device. Listing/switching spaces in a management UI and automatic garbage collection remain future work. There is no automatic TTL deletion.

## Adaptive synchronization

`SyncService` uses one executor and a monotonic clock. Foreground means that the app window is visible and has native focus. It checks `get_sync_status` every 8 seconds. An unchanged response does not fetch the roster or operations and does not animate the sync indicator. A cached roster remains signature-verified; a changed roster/epoch or resubscription requires verification before exchange.

Keep Realtime open in the background. A subscribed channel also needs a successful heartbeat within 60 seconds. After 120 quiet seconds in the background with no sendable work, checks use 30, 60, then at most 300 seconds, with bounded earlier jitter. Failed heartbeat/subscription returns to 8-second checks. Focus, show, Realtime reconnect, OS network restoration and resume request an immediate check. A two-second main-process `net.isOnline()` monitor emits transitions without DNS probes; an online result is a retry hint, not proof that Supabase is reachable. Offline startup waits for connectivity before entering SDK refresh retries. Network restoration or wake retries the saved session, including a transition received while suspension blocked work. Connectivity clears transport backoff but never a server upload quota. Sign-out/stop disposes the monitor; the existing single executor coalesces signals. A heartbeat watchdog restores bounded polling after 60 seconds without a successful heartbeat. Development-only diagnostics show network/Realtime state; production hides them. Events received during execution are retained and coalesced. Repeated or old heads are ignored within the active binding. Sleep does not replay missed timers.

Each turn reads control metadata, confirms unknown receipts independently, downloads at most one 200-operation page, then uploads at most one existing 200-operation/1 MiB batch. The apply cursor advances only through continuous replay. Upload network errors and quota cooldown do not gate status, receipt or download requests. Read failures back off for 8/16/32/60 seconds; upload and receipt retries have separate state. Normal persisted mutations request network work within 200 ms; repeated mutations do not restart that window.

The HTTP deadline starts before token acquisition and includes headers and the full body: status/receipts 5 seconds, control reads 10 seconds, pull 15 seconds and writes 30 seconds. A turn has a 60-second budget. Expiry cancels the actual HTTP/body operation. Token waits that cannot cancel are detached and cannot send late requests. Sign-out, account/workspace replacement, stop and suspend invalidate the old lifecycle. Every opened result checks that lifecycle and storage checks the captured **local** generation. The cloud generation is a separate binding; joining another device does not make those two generations equal.

Only the selected upload batch enters `send_unknown`, before network dispatch. Timeout/cancellation preserves its original identity and hash. `receipts_for` matches both before acceptance. An empty receipt is not proof of rollback; a later query or idempotent resend can confirm a delayed commit. Missing required RPCs or invalid metadata pause cloud sync with a configuration error; there is no old-protocol fallback. Manual retry can resume after configuration is repaired.

Acceptance: `pnpm test:sync-scheduling` uses the production service, SDK, storage worker and SQLite with a controlled HTTP/WebSocket cloud, plus a real native-window/renderer/IPC scenario. `pnpm test:sync-replay` covers encrypted projection and undo semantics. Reports are under `apps/desktop/output/tests/sync-cost/`. Hosted SQL, actual system sleep, packaged builds and Windows remain separate acceptance scopes.

Prepared sends use an atomic encrypted journal outside SQLite, bound to account, cloud workspace and **local** generation. Save the original payload under the stable journal key before marking the selected batch unknown; resealing uses those same bytes, even after an API key changes or an epoch advances. Missing/damaged protected payloads stop their sends instead of inventing a new hash; inaccessible legacy OS journals use the restricted recovery described above. Confirmed/applied payloads are removed. Normal workspace JSON/SQLite exports still contain only key fingerprints. Incremental secret delivery uses the same last-writer-wins comparison as storage, so an older remote/own replay cannot overwrite a newer local key. First-join secret delivery applies only winners in the committed projection, so an unsuccessful installation does not project remote keys.

## Upload protection and runtime retention

Upload waiting has a retry timestamp and a quota/network reason outside the workspace. It survives a fresh service and vault restore, is isolated by account and is checked again on resume. Foreground, notifications and manual retry can request reads during cooldown but cannot force a push. Read success does not clear upload waiting or pending data. The navigation badge and Settings show waiting/retry copy in all five languages; real downloads still show activity.

The target SQL uses versioned account limits. Initial defaults are observation-only: 6,000 new ops / 32 MiB per minute, 200,000 / 512 MiB per UTC day and 64 new device registrations per UTC day. These are generous provisional protection bounds, not measured production capacity. Enable enforcement only after hosted baseline, long-description, bulk-import, concurrent-device and expiry checks pass. Duplicate receipts do not consume new usage. Status, download and receipt APIs do not share the upload gate.

Cleanup retains device/minute buckets for 24 hours, account day/registration windows for 7 days, and non-audit `head` event hints for 7 days. Each indexed category deletes at most 5,000 rows per call with lock skipping. Operations, receipts, rosters, envelopes, recovery checkpoints and other event types are excluded. The optional named Cron job runs every five minutes with a caller-level five-second statement limit. Hosted capability/job verification is required; it is not installed by the app. Removing rows avoids growth but does not shrink allocated-disk billing.

Local acceptance evidence covers idle checks, healthy background and missed broadcasts, native focus/show, SDK reconnect, roster/epoch refresh, concurrent triggers, HTTP header/body/token stalls, late commits, upload-only cooldown, restart, stable encrypted secret retries and bounded bulk work. `supabase/tests/sync-cost-cases.sql` supplies isolated hosted integration cases for authorization, read-only status, deduplication, account quota and cleanup. Hosted concurrent transactions/Cron/live private broadcast, two physical devices, real sleep and Windows are separate pending scopes until executed.

The same account/workspace binding reuses one SDK channel. A new binding waits for the previous channel to leave; stop starts that cleanup before disconnecting the SDK. Delayed channel callbacks cannot change the current binding. Each exchange also retains its original cancellation signal across local callbacks: exceeding the turn budget releases the executor, and a late callback cannot start another exchange or update recovery state. Send-journal loads commit their in-memory context only after cancellation/revision checks.

## Security acceptance

Before changing the boundaries, cover cancellation; retained offline data/receipts; cross-account upload; unreadable vaults; failed file handoff; old-generation writes; old-cloud preservation; lost creation replies; pinned restarts; failed backup/installation; exact destructive confirmation; offline startup; reconnect deduplication; quota preservation; heartbeat expiry; timer cleanup; five-language layout/focus and production-hidden diagnostics.

`pnpm test:sync-security` runs production service/SDK/SQLite fault journeys and the native UI/IPC workflows with isolated synthetic data. `pnpm test:sync-security:packaged` repeats the native journeys in a disposable ad-hoc macOS ASAR app with test-only transport/cipher/connectivity boundaries. It publishes nothing, disables Hardened Runtime only for that test identity, and does not establish Developer ID/notarization, real-provider or Windows acceptance. Reports/screenshots and the instrumented ASAR are under `apps/desktop/output/tests/sync-security/`.

`node scripts/gen-sync-security-fixtures.mjs --check` validates deterministic signed server fixtures. `node scripts/sync-security-hosted.mjs` runs real PostgreSQL/pgTAP/RPC checks with rollback-only synthetic auth rows using the scoped development SQL token. `--apply` installs the reviewed `0009` migration only after those tests pass. It does not retrieve API keys or exercise live Google/HTTP client sessions. Server tests are `supabase/tests/0002_sync_security.test.sql`; hosted, source, instrumented package and Windows scopes remain distinct.

`pnpm test:sync-security:live` verifies the production service/SDK/SQLite against real development Supabase Auth, HTTP/RPC and private Realtime. It creates two disposable test users, verifies old encrypted rows survive recovery, checks both devices' restart pins, loses a real committed response before retry, checks scoped deletion and automatic session/upload recovery, then verifies clear-account isolation. API keys stay in memory; only this run's users and rows are removed and their absence is checked. `--browser-keys` accepts an authorized dashboard key through a one-use loopback password form when the deployment token lacks key-read permission. Evidence: `output/tests/sync-security/live/report.json`. Disposable password-auth sessions and an ephemeral local AES cipher do not establish real Google provider UI, production keychain, Wi-Fi or signed-installer acceptance.

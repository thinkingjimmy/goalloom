# Production configuration package failure cases

Recorded before the isolated CLI acceptance implementation.

Owner policy revision recorded before implementation (2026-10-25):

- Current package commercial fields, infrastructure requirements and readiness blockers must not impose the withdrawn numeric supplier-backup ceiling. Historical package-v1 and accepted D0–D3 evidence must remain unchanged.
- Removing that ceiling must preserve the 720-hour retrieval window, 168-hour online deletion deadline, restore quarantine, no user recovery from service backups and deletion replay before reopening access.
- Provider backup-policy disclosure must remain explicit. The initial backup approach is now decided by the follow-up below. No daily backup SLA, paid backup service, provider-expiry guarantee or launch authorization may be inferred.
- Tax/Managed Payments work is deferred. Existing tax validation and applicable-tax/launch gates must remain; generation must not enable tax collection or charge users.

Owner follow-up recorded before implementation (2026-10-25):

- Initial hosting stays on Supabase Free with existing local backups. No new self-hosted or paid backup service is selected. Pro may be considered after real paying users; it must not be purchased automatically or required for initial launch.
- The decided initial backup approach must not be described as pending. Post-expiry retrieval remains a separate pending discussion, with the current 720-hour rule unchanged. Provider-policy disclosure, isolation, deletion replay and all other readiness boundaries remain.
- New package-v3 and its acceptance summary must preserve historical packages-v1/v2 and their reports.

- Default execution must not read environment credentials, dotenv files, CLI authentication or the network. Poisoned deployment/provider environment variables must not affect generated bytes.
- No argument may dispatch a deployment or provisioning command. Unknown flags, including --apply, fail before generation and must not echo argument values.
- Missing Live bindings remain explicit nulls and blockers. Complete metadata is declared input, never evidence of Live verification, deployment or launch approval.
- Development project, known Test Price IDs, Apple/Test Store apps, Test mode, wrong account, duplicate prices, wrong currency/amount/interval/tax behavior and unknown fields fail closed.
- A Stripe app display name and a Product ID reused across modes are not environment evidence. Valid production declarations for the existing Stripe app or copied Product ID must remain accepted and unverified; no provider query is allowed.
- Input credentials, tokens, key material, URL credentials/query/hash and same-business-project ledger storage must not enter generated output or error text.
- A complete synthetic declaration (including the existing Stripe app and copied Product ID) must report bindings complete while deployment, launch and BILL-29 remain false. Its reserved fixture URL/tax metadata must never be treated as a provisioned service or actual tax advice.
- Source/dependency/migration drift must change the package. Verification of a changed or tampered package/checklist must fail without replacing it.
- Repeated generation over identical source, dependencies, observations and declared bindings must be byte-identical. No wall-clock timestamp, random ID, absolute machine path or environment value may enter the content.
- Existing output must not be overwritten. Partial writes cannot establish readiness. Only a local package/checklist pair is emitted.
- Missing pinned Stripe SDK, missing source/observation, invalid metadata or unsupported ledger deployment claims must stop with a finite error. No download, installation or remote fallback is allowed.
- A local passing CLI run must not claim production installation, restricted-key validation, webhook delivery, scheduler execution, backup erasure or externally enforced restore isolation.

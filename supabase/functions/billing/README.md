# Trusted billing endpoint

INPUT: Verified Supabase sessions, explicit environment/source configuration and raw signed provider requests.
OUTPUT: Account trial/status, durable billing operations, transaction-bound entitlement and retryable event work.
POS: D0–D3 billing boundary over the original billing engine, D1 continuation/presentation contracts, D2 subject resolution/deletion settlement and scoped development worker composition. No task content, sync writes, model calls or production activation.

[PROTOCOL]: Update this header when making changes, then check README.md.

`index.ts` loads Edge Secrets. `endpoint.ts` authenticates the development worker before accepting a finite request-local lifecycle scope; it resolves read-only Auth-or-subject identity before guarding the resulting subject and refuses identity creation. `handler.ts` authenticates finite actions and provider ingress. `service.ts` serializes account operations and commits provider snapshots. `providers.ts` uses Stripe Billing and RevenueCat external-purchase/subscriber APIs. `config.ts` validates fixed environment/source mappings. `http.ts` bounds bodies and validates raw-body HMAC. See [the formal contract](../../../docs/features/billing.md).

Both cycle-switch directions set `billing_cycle_anchor: 'phase_start'` on the future schedule phase at the original paid-period end. The current phase keeps its dates and price; request-level and phase-level proration remain disabled. Stripe's [phase anchor contract](https://docs.stripe.com/api/subscription_schedules/update) resets the anchor when that future phase begins. The [original A readback](../../../output/tests/billing/desktop/d3-remaining-e0938281-8b09-4753-9e36-6020f8b2464c/A-transition-anchor-readback.json) records the missing-anchor failure and remains historical evidence. The [local adapter check](../../../output/tests/billing/desktop/d3-local/phase-anchor/loopback-acceptance.mjs) verifies actual SDK serialization and refusal boundaries. Both actual transition directions subsequently passed with automatic full-price invoices, exact RC recognition and matching native state; see the [final development evidence index](../../../output/tests/billing/desktop/d3-remaining-e0938281-8b09-4753-9e36-6020f8b2464c/replacement-add75525-c69c-4774-b720-d6ef2bd0264f/acceptance-summary.md).

RevenueCat recognition matches each real paid Stripe invoice to an exact RC period and configured product/app. It accepts the current period or an explicitly paid next-period candidate only when the parent reports `has_already_renewed`; the candidate must be active, access-granting, not pending payment, non-overlapping with the current period and consistent with the latest end. Missing next-period fields inherit the parent; explicit null does not. A changed pending product is independently read and matched, so the old current product cannot block a paid phase transition. Ordinary planned changes and failed upcoming renewals never qualify. RC v1 aggregate entitlements are not a fallback. Verified future facts retain their actual invoice dates; the existing SQL `starts_at <= billing_now` and `ends_at > billing_now` access gate remains unchanged. The original renewal invoice passed development backend and native acceptance after this source fix; other lifecycle results are tracked separately below and in the formal contract.

`presentation.ts` validates immutable finite app/loopback continuations, builds canonical website return URLs and maps exact configured prices into the status catalogue. `operation.ts` represents a confirmed durable closed receipt. Completed Checkout/management replays read current authoritative status and include a matching completion receipt; cached operation results never serve as current eligibility. Portal URL recovery retains its original continuation and expiry. A callback never grants service.

The coordinator resolves exact original operations and immutable cross-device aliases before selecting a pending operation. Migration `0021` binds each recovering request's owner/environment/action/cycle/continuation to the server-selected canonical Checkout. Terminal or old canonical rows remain recoverable when a newer Checkout exists. Changing an aliased intent conflicts; no client-supplied canonical target is accepted.

Aliased terminal receipts keep canonical `operation.requestId` and add `operation.requestedId` for the authenticated caller's original request. This lets a client recover a lost first alias response without trusting an unbound operation ID. Migration `0022` atomically closes a fresh incompatible intent under its own request/action/cycle and, for navigation, immutable continuation. Existing unknown operations remain pending. Both paths use the existing finite closure reasons.

Explicit status/callback checks use `{action:'reconcile',operation?:{requestId,action:'checkout',cycle,continuation}}`. The optional operation uses the original finite Checkout intent, never a client-selected canonical ID. After normal reconciliation, migration `0024` resolves only existing owner/session-bound state. Missing/pending requests return current status without a terminal receipt; complete/closed rows use the same matched receipt contract. Changed intent conflicts. This path never calls Checkout creation, persists a new intent or opens a browser. Bare reconcile remains supported.

Every successful reconciliation reads authoritative status after pending Checkout close/complete transitions. The provider snapshot commit result can precede those transitions and is not the final response projection.

D2 source resolves an existing internal subject before every status/reconcile operation. Only an explicit live action may initialize an absent live subject. The original billing tables, operation receipts and worker remain authoritative; deleting/deleted subjects use settlement-only mode. Customer recovery accepts only the original verified provider metadata and existing subject. An empty eventually consistent customer search stays pending; it never creates a replacement customer or grants trial. See [Stripe customer search](https://docs.stripe.com/api/customers/search).

Settlement closes original Checkout/renewal work with stable operation IDs and a current billing lease. It stores verified financial facts without RC re-recognition or grace. A final active subscription discovered after the first cancellation scan keeps renewal pending for the next original-engine pass. Content/Auth deletion proceeds independently from provider failure; status reports pending or attention_required until original renewal work is resolved. Shared AI budget/fees are unchanged. These are current source contracts, not a production deployment claim.

Deploy `billing` with JWT verification disabled only because the same endpoint accepts signed webhooks; application routes always verify Auth themselves. Set callback paths `/billing/stripe` and `/billing/revenuecat`; `/billing/worker` requires its separate worker credential. Secrets: `BILLING_CONFIG` (JSON configuration), `BILLING_STRIPE_KEY` (restricted, environment-bound), `BILLING_STRIPE_WEBHOOK_SECRET`, `BILLING_RC_PUBLIC_KEY` (Stripe app v1 receipts/subscriber), `BILLING_RC_SECRET_KEY` (v2 subscriptions/products read-only), `BILLING_RC_WEBHOOK_SECRET` (HMAC), `BILLING_WORKER_SECRET`. Supabase injects service-role/Auth access. No client key can call billing RPCs. HMAC is mandatory, with a five-minute signing-time tolerance.

The worker must run at least once per minute. Each invocation claims at most two events and two due accounts and shares one fresh reconciliation per account. Its response includes total worker elapsed time. Development worker POSTs accept only `/billing/worker` or the gateway path `/functions/v1/billing/worker`, require the existing credential, then require `x-goalloom-lifecycle-scope` in the existing UUID-dot-64-hex form. Lifecycle RPC and `workerScopeGuard` recheck each call; SQL retains claim/write fences. Concurrent requests never share a mutable scope. Production and non-worker composition remain as before. Keep the old unscoped development cron inactive. Loopback scope checks do not establish deployed SQL, provider or scheduler acceptance. Before paid rollout, configure and verify the scheduler plus Stripe custom retries; do not rely on invocation after a webhook response. A deployment without a working scheduler is incomplete.

Only `lifecycle_identity` resolves its existing Auth-or-subject parameter before the target check. The worker requires `p_create:false`, checks the active scope, performs read-only resolution, then checks the returned subject and any distinct Auth owner. Other owner parameters retain their existing meaning. The shared lifecycle RPC transport accepts successful empty acknowledgements as null, including PostgREST204; empty failures, malformed nonempty JSON and oversized replies remain failures. An error after a void write does not establish rollback; read back the original event/lease outcome.
